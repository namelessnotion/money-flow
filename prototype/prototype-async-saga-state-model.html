Async, Kafka-driven saga vs. today's in-process sync saga

The question this demo answers: today's runSaga folds a Transfer/Transaction's own event stream and dispatches the next step synchronously, in-process. If instead a saga orchestrator reacts to domain events delivered through Kafka — where delivery can be delayed, duplicated, or reordered, publication can happen via CDC or a polling relay, topics can be unified or split per aggregate type, and Ruby (or any CQRS-style read model) consumes the same stream independently — does the Transfer/Transaction state model still reach correct terminal outcomes, or does it produce states the pieces would disagree about? Use the buttons below freely, or step through a guided scenario in the tabs — the interesting moments are the ones where something looks like it shouldn't be possible.

The fuzzer picks uniformly from whatever is legal right now — domain steps, publishes, duplicates, reorders, consumes, crashes — and stops the instant an invariant is violated, leaving the model and the activity log sitting on the reproduction. It never touches publisher mode, topology or handler semantics: those are the knobs under test, so set them first and hunt under each. Runs are seeded and the seed is reported, so a hit is replayable.
