# CDC tracer bullet: Postgres → Kafka

**Status:** ran 2026-09-07, on the local development stack.
**Verdict:** all four claims proven. [`docs/adr/0001`](adr/0001-async-event-driven-saga-and-postgres-to-kafka-publication.md) stands as written; no custom SMT is needed.

This is the thin end-to-end slice [`docs/adr/0001`](adr/0001-async-event-driven-saga-and-postgres-to-kafka-publication.md)
was decided without. It is infrastructure only — nothing in `go/`, `ruby/` or `client/` reads from Kafka, and
`runSaga` is untouched. Its value is the finding, not the code.

## Running it

```
docker compose up -d
docker/cdc/setup.sh                              # scratch db, schema, connector
docker compose exec -e DATABASE_URL="postgres://money_flow:money_flow@postgres:5432/money_flow_cdc?sslmode=disable" \
  go go run ./cmd/cdctracer                      # appends real events
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic transfer-events --from-beginning --timeout-ms 8000 \
  --property print.key=true --property print.partition=true --property print.offset=true
docker/cdc/teardown.sh                           # connector, slot, scratch db
```

The events are generated by `go/cmd/cdctracer`, which writes through `eventstore.PostgresStore.Append` — the
same path the sagas use. Nothing is hand-written with `psql`, so the pipeline sees what the application actually
produces. It writes to a scratch `money_flow_cdc` database, never `money_flow_dev`: the `events` table is
append-only, so tracer rows would otherwise be permanent.

## The four claims

### 1. `wal_level = logical` works here — **proven**

`command: postgres -c wal_level=logical` on the existing service, no volume recreated.

```
 wal_level
-----------
 logical

 aggregate_type | count        -- money_flow_dev, unchanged across the restart
----------------+-------
 holder         |   197
 wallet         |    84
```

The slot exists and its lag is a plain query:

```sql
SELECT slot_name, active, restart_lsn, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS lag
FROM pg_replication_slots WHERE slot_name = 'money_flow_cdc_events';
```

```
slot_name           | money_flow_cdc_events
active              | t
restart_lsn         | 0/35EBBE0
confirmed_flush_lsn | 0/35ED8E8
lag                 | 616 bytes
```

`REPLICA IDENTITY` is `DEFAULT` (`relreplident = 'd'`), which was checked rather than assumed. It is adequate:
`pgoutput` sends the full new tuple for an INSERT regardless of replica identity, and the table's
`BEFORE UPDATE`/`BEFORE DELETE` triggers mean there are no other operations to decode. The append-only triggers
never fired and never interacted with the slot.

### 2. Routing by `aggregate_type` — **proven**

One table, thirteen rows, two topics. Both were auto-created with three partitions:

```
transaction-events
transfer-events
```

Eleven `transfer` rows landed on `transfer-events`, two `transaction` rows on `transaction-events`, with no
cross-contamination.

Producer idempotence (ADR decision 5) is on. From the connector task's own `ProducerConfig` in the Connect log:

```

	client.id = connector-producer-money-flow-events-0
	enable.idempotence = true
```

worker (`CONNECT_PRODUCER_ENABLE_IDEMPOTENCE`) rather than per connector (`producer.override.*`) was verified to
be sufficient on its own, so there is one owner of that fact and it covers any connector registered later.

### 4. No custom SMT is needed — **proven**

A consumer reads `event_type` and `aggregate_id` straight out of the JSON body and the message key. This
consumer never touches `payload`:

```
wake up: transfer 01a07ef8-3437-79bc-9af9-eb2076c5b857 -> transfer.v1.TransferRequestAccepted (seq 1)
wake up: transfer 01a07ef8-3437-79ba-9519-daf863185358 -> transfer.v1.TransferRequestAccepted (seq 1)
wake up: transfer 01a07ef8-3436-76c8-a39f-d3f409f08f3c -> transfer.v1.TransferRequestAccepted (seq 1)
```

`payload` is base64 exactly as ADR 0001 predicted, and it really is the protobuf — decoding
`CiQwMWEwN2VmOC0zNDMxLTcxZGUtYWMyOS1lNmYwMzQ3MzJkYjY=` gives
`\n$01a07ef8-3431-71de-ac29-e6f034732db6`, field 1 of `TransferRequestAccepted`. Skipping it is a choice the
message shape allows, not a limitation being worked around.

## The SMT decision

**Debezium's bundled `io.debezium.transforms.outbox.EventRouter`, with its field names configured. No custom
code, no extra jars, no scripting engine.** This is the gotcha the issue flagged, and it resolves in the ADR's
favour — the router's column names are all configurable:

```json
"transforms.outbox.table.field.event.id": "global_seq",
"transforms.outbox.table.field.event.key": "aggregate_id",
"transforms.outbox.table.field.event.type": "event_type",
"transforms.outbox.table.field.event.payload": "payload",
"transforms.outbox.route.by.field": "aggregate_type",
"transforms.outbox.route.topic.replacement": "${routedByValue}-events",
"transforms.outbox.table.fields.additional.placement": "aggregate_type:envelope,event_type:envelope,sequence:envelope,global_seq:envelope"
```

The `aggregatetype` / `aggregateid` / `payload` naming in Debezium's documentation is a default, not a
requirement. `route.by.field` plus `route.topic.replacement` gives claim 2, `table.field.event.key` gives
claim 3, and they cost one line of configuration each.

`table.fields.additional.placement` is what makes claim 4 hold. Left alone, `EventRouter` publishes the payload
column *as* the message body, which is exactly backwards for an event log whose payload is deliberately opaque:
consumers would get a base64 blob and have to read headers for everything they actually want. Placing the
columns into the envelope restores the column-shaped message both consumers need, while keeping the router's
routing and keying.

**Considered and rejected: plain table CDC with `message.key.columns` and `ContentBasedRouting`.** That path
also works without custom code, and its `ExtractNewRecordState` output is arguably the more natural shape. It
costs more, though: `ContentBasedRouting` needs the scripting SMT and a JSR-223 engine enabled in the image, and
keying needs a second stock SMT to unwrap `message.key.columns`' struct. `EventRouter` reaches the same message
with one transform and nothing added to the image.

**ADR 0001 needs no amendment on cost grounds.** Its polling-vs-CDC argument survives intact.

## Not demonstrated

**The `global_seq` commit-order gap.** ADR 0001's strongest argument against a polling relay is that
`GENERATED ALWAYS AS IDENTITY` allocates at INSERT and publishes at COMMIT, so a relay ordering by `global_seq`
can permanently skip an event. Eight concurrent appends were run specifically to try to catch it; every
partition came out monotonic in `global_seq`, so no inversion was observed.

That is a null result, not a refutation. Observing one reliably needs a transaction held open across another's
commit, which `eventstore.Store` deliberately does not expose, and the property it would demonstrate is a
documented consequence of Postgres identity semantics rather than something CDC introduces. Recorded here so a
future reader does not mistake the absence for evidence either way.

## Reverting

`docker compose down` leaves one thing behind: **the replication slot**, which lives in the long-lived
`money_flow_postgres` volume. A slot with no consumer pins WAL until the disk fills. `docker/cdc/teardown.sh`
drops it, along with the connector and the scratch database — run it *before* `docker compose down`, since it
needs both Connect and Postgres up:

```
docker/cdc/teardown.sh
docker compose down
git checkout main
docker compose up -d
```

If the stack is already down, bring Postgres back and drop the slot by hand:

```sql
SELECT pg_drop_replication_slot('money_flow_cdc_events');
```

The slot must be inactive first — delete the connector, or stop the `connect` service, and the walsender exits.

Topics are not dropped by `teardown.sh`. The `kafka` service has no volume, so `docker compose down` discards
them along with the broker; a teardown/setup cycle *without* a `down` in between republishes into the topics
already there, which is why a second run shows 22 and 4 messages rather than 11 and 2.

Verified after the run, with the rig up: Go suite `go test ./...` all green, Ruby suite 39 examples / 0
failures, `golangci-lint run ./...` 0 issues.
